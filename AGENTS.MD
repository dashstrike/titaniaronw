# Project Instructions

## Context & Environment
- Read `README.md` before multi-file changes, deployment work, or architectural changes. Read `discord/README.md` before changing anything under `discord/`.
- Verify documentation against the current code. The repository contains a Laravel application, a GitHub Pages static export, a Supabase backend, and a separately deployed Cloudflare Worker.
- **Local**: Laragon on Windows. The Laravel development server normally uses `http://127.0.0.1:8015`.
- **Static production**: GitHub Pages, generated by `php artisan pages:export` and deployed by `.github/workflows/pages.yml`.
- **Optional PHP production**: Ubuntu Laravel hosting. Do not assume this is the active production target.
- **Discord production**: Cloudflare Worker under `discord/`, deployed separately and kept on Workers Free.
- Tailor commands, paths, services, permissions, and configuration to the applicable environment. If the target is unclear and the commands differ materially, ask whether the task is for Laragon, GitHub Pages, Ubuntu, Supabase, or Cloudflare first.

## Architecture Boundaries
- Laravel routes, controllers, Blade templates, and static export logic are the application shell. Supabase remains the runtime database and authentication backend in both Laravel and GitHub Pages modes.
- The same Blade views must remain compatible with normal Laravel rendering and `php artisan pages:export` unless the request explicitly targets only one mode.
- There is no Vite or npm frontend build. Browser JavaScript, CSS, fonts, icons, and libraries are committed under `public/` and loaded directly.
- The Discord attendance integration is an independent Node.js 22 Cloudflare Worker in `discord/`. Do not mix its deployment, dependencies, secrets, or tests with Laravel deployment.
- Keep feature work within the established file organization: `resources/views/`, `public/js/`, `public/css/`, `app/`, `routes/`, `sql/`, `supabase/migrations/`, and `discord/`.

## Mandatory Documentation Sync
- Every implemented change that affects features, behavior, workflows, routes, configuration, database objects, permissions, setup, testing, deployment, or repository structure MUST update the relevant documentation in the same task.
- Update the root `README.md` for application-wide or website changes. Update `discord/README.md` for Discord Worker changes. Update both when a change affects integration between the website and Worker.
- Keep documentation consistent with the final verified implementation. Remove or revise obsolete statements instead of only appending new text.
- Document any required PostgreSQL SQL, configuration variables, deployment order, compatibility concern, limitation, and verification command needed to use the change safely.
- Do not add a changelog entry or edit documentation for a purely internal formatting/comment change that does not affect behavior or usage.
- Before completing a code task, explicitly check whether the relevant README reflects the change. Do not report the task complete while required documentation is missing.

## Strict Database & Supabase Rules (NEVER VIOLATE)
- The application database is **Supabase PostgreSQL**, not MySQL. Do not write MySQL-specific SQL or assume Laravel's default database connection owns application data.
- NEVER create, edit, run, or recommend Laravel migrations in `database/migrations/`. NEVER run `php artisan migrate`, `migrate:fresh`, `migrate:refresh`, `migrate:reset`, `db:seed`, or `db:wipe`.
- NEVER execute live SQL or mutate a Supabase project without explicit instruction identifying the target project and authorizing the change.
- For requested schema or data changes, provide or update exact PostgreSQL SQL for manual review. Follow the repository's existing `sql/` and `supabase/migrations/` conventions; inspect related scripts before choosing the correct location.
- Do not run all files in `sql/` as a batch. They include historical setup, feature upgrades, tests, and scripts that may modify existing data.
- Before implementing a Supabase feature, verify current Supabase documentation and relevant breaking changes. Do not guess CLI commands; use `supabase --help` and the relevant subcommand `--help`.
- Any table exposed through the Data API must have RLS enabled and policies matching the real authorization model. Do not treat `TO authenticated` alone as authorization.
- UPDATE policies require appropriate SELECT access plus both `USING` and `WITH CHECK`. Do not use user-editable metadata for authorization.
- Prefer `SECURITY INVOKER`. Do not add `SECURITY DEFINER` merely to bypass a permission error. If it is genuinely required, restrict execution, set a safe `search_path`, validate the caller, and review exposure carefully.
- Views exposed through the API must respect RLS, normally with `security_invoker = true`, or be explicitly protected from API roles.
- Verify database work with a focused test query and security/advisor checks when access is available. Local PHP and synthetic JavaScript tests do not prove that deployed RLS, functions, or data are correct.

## Laravel & PHP Style
- Use simple, direct Laravel code and match the patterns already present in the same module. Do not introduce repositories, service layers, DTOs, packages, or design patterns unless that module already uses them or the user approves the change.
- Keep changes strictly scoped. Do not refactor, rename, or reformat unrelated code.
- Match existing naming, route, controller, Blade, and formatting conventions. If the relevant pattern is unclear and the proposed code could diverge, ask the narrowest blocking question.
- Do not install or update Composer packages without explicit approval. Preserve `composer.lock` when dependencies are intentionally changed.
- Preserve static-export compatibility. Do not introduce runtime-only PHP behavior into exported pages without providing the established static equivalent.

## Blade, CSS & JavaScript Rules
- Follow the existing layouts and partials in `resources/views/`. Reuse the current Darkone/template component structure.
- Reuse existing CSS classes, JavaScript modules, icons, and locally bundled assets. Search `public/css/`, `public/js/`, `public/vendor/`, and nearby Blade templates before adding markup or behavior.
- Do not invent CSS classes, create CSS files, add `<style>` blocks, or use inline `style=""` attributes unless the user explicitly requests custom styling for that element. If no suitable pattern can be found, ask for direction.
- Keep feature JavaScript in the existing relevant file under `public/js/`; do not add inline scripts when the module already has an external script.
- Do not add CDN dependencies. Browser libraries are served locally from `public/vendor/`. When an approved library update is required, pin the version, preserve its license, update `public/vendor/browser-assets.json`, and commit the lockfile where applicable.
- Preserve asset cache-busting patterns already used by the Blade templates and exporter.
- Treat `public/config.js` and other browser files as public. Never place privileged keys, service-role credentials, bot tokens, or secrets in them.

## Discord Worker Rules
- Read `discord/README.md`, `discord/package.json`, and `discord/wrangler.toml` before changing or deploying the Worker.
- Use Node.js 22 and `npm ci` inside `discord/`; do not run a root npm workflow because none exists.
- Keep the Worker on Cloudflare Workers Free. Do not enable a paid plan or add paid infrastructure without explicit approval.
- Preserve the existing Durable Object namespace and bindings. Do not delete or recreate them; they store account links, message registrations, and duplicate-delivery receipts.
- Store secrets only through Cloudflare secrets. Never print, copy into code, or expose `DISCORD_BOT_TOKEN`, `DISCORD_PUBLIC_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, or equivalent privileged values.
- Preserve the explicit website-origin allowlist. Do not replace it with wildcard CORS.
- Do not deploy the Worker, register Discord commands, post messages, or modify live attendance unless explicitly requested.

## Testing & Verification
- Run the smallest relevant checks first, then broaden only when risk justifies it.
- PHP/Laravel: use `php artisan test --filter=TestName` for targeted work. Use `php artisan test` when changes span shared rendering, exporting, routes, or multiple features.
- Static export: run `php artisan pages:export` when changing routes, Blade output, asset loading, redirects, or exporter behavior. Remember that this replaces `storage/app/pages`.
- Browser JavaScript: run the relevant file in `tests/js/` with Node. Use the established browser tests in `tests/browser/` only when their prerequisites are available.
- Discord Worker: from `discord/`, use the test scripts defined in its `package.json`; use its documented dry-run command before deployment-related changes.
- Tests must not require or mutate the live Supabase project unless the user explicitly requests an integration check and identifies the safe target.
- Report what was tested and any unverified deployment or browser behavior concisely.

## Deployment Safety
- GitHub Pages, Ubuntu Laravel hosting, Supabase SQL, and the Cloudflare Worker are four separate deployment surfaces. Never imply that deploying one updates the others.
- Do not run deployments, GitHub workflows, Supabase SQL, Cloudflare commands, or production server commands without explicit user authorization.
- Preserve the existing Supabase project distinction. Respect `TITANIA_DEVELOPMENT_PROJECT`; never export or deploy a build connected to the development project.
- Preserve the current Laravel `APP_KEY` on existing installations.
- Before release advice, identify all required coordinated frontend, SQL, Worker, and configuration changes in their required order.

## Git Rules
- Never run `git commit`, `git push`, create branches or tags, open pull requests, or trigger workflows unless explicitly instructed.
- Leave changes unstaged for review unless the user explicitly asks otherwise.
- Do not discard or overwrite unrelated local changes. Inspect `git status` and relevant diffs before editing overlapping files.

## Security & Secrets Rules (NEVER VIOLATE)
- NEVER read, inspect, print, search, or modify `.env`, `.env.*`, `discord/.dev.vars*`, credentials, private keys, or secret stores. `.env.example` and documented variable names are safe to inspect.
- Never expose a Supabase service-role/secret key in browser code, GitHub Pages output, logs, tests, documentation examples, or chat. Browser code may use only the established public/publishable configuration protected by RLS.
- Do not weaken RLS, authentication, origin checks, Discord signature validation, role checks, or authorization to make a feature work.
- Treat generated static output as public. The exporter must continue rejecting privileged keys and development-project configuration.

## Output & Efficiency Rules
- Lead with the exact code, PostgreSQL SQL, command, or configuration when no clarification is required.
- Name each changed file and make insertion or replacement points unambiguous. Organize multi-file answers by path.
- Use `rg`, `rg --files`, and targeted line reads instead of dumping large files. Summarize test failures briefly and include the actionable error.
- Ask only the narrowest blocking question when required context or authorization is missing.
- Avoid lengthy introductions, generic conclusions, unnecessary abstractions, and speculative improvements.
